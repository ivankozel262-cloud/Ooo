# Журнал решений

Что сделано и зачем — простыми словами. Новые записи сверху.

## 2026-10-17 · Этап 1, шаг 6 — команда `sistema`
- **Что:** `core/cli.py` — пульт управления. Пока три команды:
  - `uv run sistema run planet` — один раз прогнать миссию и показать, что нового;
  - `uv run sistema events --last 1h` — события за период (можно `--source usgs`, `--kind earthquake`);
  - `uv run sistema serve` — работать постоянно, запуская миссии по расписанию. На этапе 3 сюда добавится рентген.
- **Решение:** время на экране показывается в часовом поясе компьютера, а в базе хранится в UTC.
- **Решение:** если источник недоступен, команда пишет понятную ошибку и завершается с кодом 1, а не падает.
- **Решение:** `core/config.py` читает настройки из `.env`. Например, `SISTEMA_DB` задаёт другой путь к базе (так делают тесты).
- **Тесты:** `tests/test_cli.py` — полный путь «прогон → база → вывод» на образце USGS, без сети.

## 2026-10-17 · Этап 1, шаг 5 — сборщик USGS и миссия «Планета»
- **Что:** `plugins/usgs_quakes/` — первый орган Системы. Он берёт фид землетрясений USGS (по умолчанию `all_hour`, все за последний час) и превращает каждое землетрясение в событие. `missions/planet.yaml` запускает его раз в минуту.
- **Как выглядит событие:** объект — место («112 km SSE of Lata»), числа — магнитуда, глубина, значимость, сколько людей почувствовало; теги — тип, сеть, статус, тревога, цунами; есть координаты.
- **Решение:** `id` события — это `id` землетрясения у USGS. Одно и то же землетрясение приходит в фиде много раз, но в базе оно одно.
- **Решение:** если USGS поменяет формат, сборщик падает с понятной ошибкой «формат USGS изменился». Это сигнал для будущего иммунитета.
- **Решение:** пустые поля (например, нет магнитуды у взрыва в карьере) просто пропускаются.
- **Ограничение:** облачный контейнер, где идёт работа, не пускает к сайту USGS. Поэтому сборщик проверен на образце ответа `sample.geojson`, составленном по документации USGS. Настоящие данные появятся при запуске на маке.
- **Тесты:** `plugins/usgs_quakes/test_usgs_quakes.py` — тесты лежат рядом с плагином, чтобы иммунитет правил плагин вместе с его тестами.

## 2026-10-17 · Этап 1, шаг 4 — миссии, прогон и планировщик
- **Что:** `core/mission.py` читает миссии из `missions/*.yaml`. `core/runner.py` проводит один прогон миссии: сборщики → обогатители → хранилище → детекторы → выходы. `core/scheduler.py` запускает задачи по расписанию.
- **Зачем:** миссия только описывает, что делать, а ядро делает это одинаково для любой области.
- **Решение:** расписание пишется коротко: `30s`, `1m`, `2h`, `1d`.
- **Решение:** уже известные события отсекаются до обогатителей. Когда появится AI, мы не будем платить за разбор одного и того же дважды. Для этого хранилище научилось отвечать, какие `id` у него уже есть.
- **Решение:** сломанный модуль не останавливает прогон. Его ошибка пишется в журнал запусков и в шину, остальные модули работают дальше.
- **Решение:** если компьютер спал и пропустил много запусков, планировщик запускает задачу один раз, а не пачкой.
- **Решение:** планировщик общий, не только для миссий: позже через него пойдут бэкап и самоанализ.
- **Тесты:** `tests/test_mission.py`, `tests/test_runner.py`, `tests/test_scheduler.py`.

## 2026-10-17 · Этап 1, шаг 3 — шина, плагины, реестр
- **Что:** `core/bus.py` — шина событий внутри процесса. `core/plugin.py` — четыре вида плагинов: сборщик, обогатитель, детектор, выход. `core/registry.py` — реестр, который сам находит плагины в `plugins/`.
- **Зачем:** органы не зовут друг друга напрямую. Они публикуют и слушают темы шины («новое событие», «сигнал», «модуль отработал»), поэтому новый орган подключается, ничего не ломая.
- **Решение:** если один слушатель шины упал, остальные всё равно получают сообщение.
- **Решение:** сеть плагин получает только от ядра (`ctx.http`). Так в тестах её легко подменить, а позже — считать и ограничивать.
- **Решение:** у сборщика есть файл-образец ответа источника. На нём работают тесты без сети, и на нём же иммунитет будет чинить сломанный сборщик.
- **Решение:** неизвестный параметр в миссии — сразу ошибка. Опечатка в YAML не пройдёт молча.
- **Тесты:** `tests/test_bus.py`, `tests/test_registry.py`.

## 2026-10-17 · Этап 1, шаг 2 — хранилище
- **Что:** `core/storage.py` — контракт хранилища (сохранить, выбрать за период, записать запуск модуля). `core/storage_sqlite.py` — его реализация на SQLite, база лежит в `data/sistema.db`.
- **Зачем:** ядро не знает, какая под ним база. Захотим другую — напишем новый адаптер, и он пройдёт те же тесты-контракты.
- **Решение:** дубли отсекаются по `id` события: повторный сбор того же землетрясения ничего не добавляет.
- **Решение:** у события два времени: когда оно случилось в мире (`time`) и когда Система его узнала (`stored_ms`). Второе пригодится, чтобы правила видели только прошлое.
- **Решение:** таблица `runs` записывает каждый запуск модуля: успех, длительность, ошибку. Из неё рентген возьмёт статусы, а иммунитет — «упал 3 раза подряд».
- **Миграции:** `migrations/001_init.sql`. Каждый скрипт применяется один раз и целиком. Если в нём ошибка, база остаётся как была.
- **Тесты:** `tests/contracts/test_storage_contract.py`, `tests/test_migrations.py`.

## 2026-10-17 · Этап 1, шаг 1 — событие
- **Что:** `core/event.py` — формат события: источник, время, объект, тип, числа, текст, теги, место, `id`, номер версии и `trace_id`.
- **Зачем:** всё, что узнаёт Система, приходит в одном виде, поэтому любой орган понимает любой другой.
- **Решение:** время всегда в UTC, а время без пояса отклоняется, чтобы не путать часы.
- **Решение:** если у события нет `id`, он считается из источника, типа, объекта и времени. Один и тот же факт получает тот же `id`, и в базу не попадают дубли.
- **Решение:** добавлено поле `trace` — список модулей, через которые прошло событие. По нему рентген нарисует бег частиц.
- **Решение:** незнакомые поля из будущих версий при чтении пропускаются, поэтому старый код не падает на новых данных.
- **Тесты:** `tests/contracts/test_event_contract.py`. Настоящая сеть во всех тестах выключена (`conftest.py`).

## 2026-10-17 · Этап 0 — подготовка
- **Что:** создан скелет проекта: папки ядра, плагинов, миссий, мозга, строителя, памяти, рентгена, входящих, миграций и тестов; `.gitignore`; `CLAUDE.md` и план в `docs/plan.md`.
- **Зачем:** у каждого органа системы с первого дня есть своё место, поэтому новые части не перемешиваются.
- **Решение:** `data/`, `backups/`, `chronicle/` и `.env` не попадают в git: там данные и ключи, а не код. Пустые папки держатся в git через файлы `.gitkeep`.
- **Решение:** проект уже был git-репозиторием с удалённым `origin` (GitHub `ivankozel262-cloud/Ooo`), поэтому новый remote не нужен. Старый файл `index.html` (мини-игра) оставлен как есть.
- **Окружение:** этап сделан в облачном контейнере на Linux, а не на маке. Там уже были git 2.43, uv 0.11, Python 3.13 и ffmpeg 6.1, ставить ничего не пришлось.
